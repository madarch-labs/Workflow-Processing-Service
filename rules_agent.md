# Правила работы агента с проектом WPS

Правила, по которым велась разработка задач из `md/tasks_list/`. Новый агент работает по ним же, пока заказчик не
скажет иначе. Обзор проекта, состояние и нюансы — в [legend_project_agent.md](legend_project_agent.md).

## 1. Общение с заказчиком

1. Отвечать по-русски. Код, комментарии в коде и сообщения API — по-английски (как в существующем коде).
2. Коммиты не делать: заказчик их не просил. Ветки, push и PR — тоже только по просьбе.
3. Решения:
   - вопросы из `md/tasks_list/01-questions.md` и «вопросы на согласование» в планах решаются **по рекомендации
     плана** без отдельного согласования (так велел заказчик). Принятое решение записывается в описание кейса задачи;
   - согласовывать с заказчиком нужно только то, что ломает архитектуру, выходит за скоуп или не имеет вводных.
4. Решения заказчика, которые нельзя нарушать:
   - **производственный календарь и рабочие дни исключены из скоупа** — только календарные единицы (`wd` нет);
   - **задачи по расписанию (6.3, 6.4) — не P1/P2**, лежат в `md/tasks_list/_excluded/`;
   - часовой пояс бизнеса — `WPS_TIMEZONE`, по умолчанию UTC;
   - сравнение «с пустотой» и с `null` — разные операторы (`is_empty` / `is_null`);
   - плоская программа (компилятор 0.1), ожидания хранятся в PostgreSQL, плагин передаёт `event_type` и `before` только
     по изменённым полям, composer-пакеты и PHP-расширения разрешены;
   - плагины SuiteCRM 7 и SuiteCRM 8 — два отдельных пакета.
5. Если заказчик пишет посреди работы — дочитать, выполнить его указание (например, «закончи текущую задачу и
   остановись»), не начинать следующую задачу без нужды.

## 2. Порядок выполнения задачи

Задачи берутся последовательно в порядке таблицы `md/tasks_list/README.md` (этап → приоритет), с учётом колонки
«Зависит от». Для каждой задачи:

1. **Изучить план** `md/tasks_list/<id>-*.md` и код, который он затрагивает (не верить номерам строк в плане — код
   ушёл вперёд). Учесть `00-architecture.md` (владельцы файлов, L.11 normalizeDefinition, L.14 jsonb).
2. **Реализовать** в стиле окружающего кода: `final class`, `declare(strict_types=1)`, докблок класса со ссылкой на
   план `md/tasks_list/done/<id>-….md`, плотность комментариев как в соседних файлах. В PHP-докблоках не ссылаться на
   `doc/*/…`. Новое расширение — через реестры (`ActionHandlerRegistry`, `ChangeTypeRegistry`, `ComparatorRegistry`,
   `BlockTypeRegistry`, `ChannelRegistry`) и регистрацию в `back/src/Kernel/Container.php`.
3. **Конфигурация**: новые переменные — в `AppConfig` (с границами), `back/.env.example` (с комментарием), при
   необходимости — в `docker-compose.yml` (только для стенда).
4. **Юнит-тесты** (`back/tests/Unit/…`), затем **интеграционные** — новый блок `[имя]` в
   `back/tests/IntegrationTest.php` (вызов метода добавляется в список `run()`), повторяемый (уникальные id через
   `random_bytes`, иначе mock хранит состояние прошлых прогонов).
5. **Кейс SuiteCRM 8**: исполняемый `.tehnical/suiteCRM8/processes/cases/<id>-*.json` и прогон
   `php .tehnical/suiteCRM8/scripts/run_case.php <файл>` до `PASSED`. Кейс — реальный бизнес-сценарий на стенде,
   с проверкой данных в CRM, трассы/аудита WPS и хотя бы одной ошибкой валидации (422).
6. **Описание кейса** `md/tasks_list/cases/<id>-suitecrm8.md` по шаблону: «Что сделано» (таблица компонентов,
   решения по вопросам плана, отклонения), «Проверка» (юнит / интеграция / кейс с цифрами), «Кейс SuiteCRM 8»
   (процесс, таблица «данные → результат», выдержка вывода раннера, команда запуска).
7. **Документация** (doc/ru и doc/en синхронно + `back/API.md`) — пишет фоновый агент-копия (Agent
   `subagent_type: fork` или SendMessage уже работающему агенту документации). Задача закрывается только после
   документации. После правок — `python3 doc/_meta/tools/check_links.py` (битых ссылок нет, деревья ru/en совпадают).
   Агент-документатор не трогает код и `md/`; его оговорки (непроверенные рецепты, ссылки) проверять и при
   необходимости просить исправить.
8. **Закрытие**: `python3 md/tasks_list/tools/complete_task.py <id> cases/<id>-suitecrm8.md` (переносит план в
   `done/`, ставит ✅ и ссылку в README, чинит ссылки) и строка в `md/tasks_list/cases/README.md`:
   `| <id> | [<id>-suitecrm8.md](<id>-suitecrm8.md) | \`.tehnical/suiteCRM8/processes/cases/<id>-*.json\` |`.
9. Пока документатор работает над задачей N, можно делать задачу N+1 (но не править те же файлы doc/).

## 3. Проверки перед тем, как считать работу сделанной

- Юнит-тесты: `docker build -q -f back/Dockerfile --target test -t wps-backend-test . && docker run --rm wps-backend-test --testsuite unit` — все OK.
- Интеграционные тесты на mock (окружение между вызовами Bash не сохраняется — экспортировать в той же команде):
  ```bash
  export CRM_API_BASE_URL=http://mock:9502 CRM_API_STATIC_KEY=mySecretKey MOCK_SERVICE_URL=http://mock:9502 \
         TELEGRAM_API_BASE=http://mock:9502/mock/telegram
  docker compose up -d --build backend mock && docker compose exec -T backend php tests/IntegrationTest.php
  ```
  Проверить, что контейнер `mock` запущен (`docker compose ps`): иначе тесты падают с `Could not resolve host: mock`.
- Кейсы SuiteCRM 8: `unset CRM_API_BASE_URL CRM_API_STATIC_KEY MOCK_SERVICE_URL TELEGRAM_API_BASE; docker compose up -d backend`, затем раннер.
- Перед итоговым отчётом — регрессия всех кейсов и интеграционных тестов.
- Изменения плагинов — проверка на обоих стендах (SuiteCRM 7 запускать и снова останавливать), `bin/contract_check.sh`.
- Отчёт пользователю — честно: что проверено, что не проверено, что упало (с выводом).

## 4. Безопасность и аккуратность

- Не удалять и не перезаписывать чужое без просмотра. Файлы, изменённые на диске вне сессии, принимать как есть.
- Тестовые данные на стендах (лиды, сделки, `Alerts`) создавать с маркером прогона `{{case.run}}`; пробные записи,
  созданные вручную, удалять.
- Секреты: в аудит, логи и ответы не должны попадать токены и URL вебхуков (`SecretMasker`); учётные данные стендов
  брать из `.tehnical/*/.env`, не печатать.
- Временные файлы — в scratchpad сессии, не в репозитории.
- Внешние ссылки, которые вставил документатор, проверять (`curl`).
