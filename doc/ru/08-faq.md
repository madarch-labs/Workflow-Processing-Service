## Процессы и условия

### Процесс не запустился. Что проверить?

Пройдите по списку:

1. Процесс **активен**: на карточке метка «Активен». Новый процесс сохраняется неактивным, если не нажать
   **Сохранить и активировать**.
2. Это **процесс верхнего уровня**. Ведомые процессы к событиям CRM не подбираются, их запускает только `start_process`.
3. **Тип объекта** совпадает с `module` (или `object_type`) события, включая регистр: `Deals`, а не `deals`.
4. **Тип события** входит в `trigger_on` процесса: процесс с `["update"]` не запускается при создании записи, с `[]` —
   вообще не запускается событиями. Поле видно в ответе `GET /api/processes/{id}`.
5. **Условия** выполнены. Запустите процесс вручную с тем же объектом — диалог покажет результат каждого условия.
   Условия **Изменилось** требуют в объекте `event_type`, `changed_fields` и `before`.
   См. [Ручной запуск и сброс](03-user-guide/manual-run-and-reset.md).
6. Не мешает **однократный запуск для записи**. Проверьте вкладку «Однократные запуски».
7. Событие корректно. Событие без `id` или без `module`/`object_type` уходит в стрим недоставленных сообщений
   `crm_events:dlq` и не попадает ни в один процесс. См. [Решение проблем](04-operations/troubleshooting.md).

Событие, не прошедшее условия, выполнения не создаёт и в журнал не попадает — пустой журнал не значит, что событие не
пришло.

### Какие действия можно настроить в интерфейсе, а какие только через API?

В редакторе — условия «И» с одним текстовым значением, предзагрузка, строки **Изменение** и **Сохранить в CRM**,
**Запустить следующий процесс**. Письма, HTTP-запросы, уведомления, назначение ответственного, поиск записей, массовое
изменение, циклы, ветвления, паузы, `set_variable`, `stop_process`, `trigger_on`, константы, условия с `cast`, списками
и группами «ИЛИ» — через JSON-определение (`POST` / `PUT /api/processes`). Таблица — в
[Обзоре](01-overview/index.md#что-настраивается-в-редакторе-а-что-через-api), готовые JSON — в
[Рецептах](03-user-guide/recipes.md).

### Можно ли открыть в редакторе процесс, созданный через API?

Да, и открыть, и сохранить. Форма правит определение поверх исходного JSON: если открыть процесс и нажать
**Сохранить** без правок, определение не изменится (вырастет только `version`). При сохранении:

- константы `definition.constants` и другие ключи определения, которых нет в форме, остаются;
- у строк условий, изменения, сохранения, предзагрузки и запуска процесса остаются поля, которых нет в форме: `cast`,
  `cast_options`, `on_cast_error`, `id`, `on_error`, `retry`, `mode`, `strategy`; числа и логические значения не
  превращаются в строки;
- строки **Запустить следующий процесс** остаются на своих местах в списке действий; новые строки добавляются в конец;
- если в строке сменить оператор или тип изменения, настройки старого вида сбрасываются; остаются только `cast`,
  `cast_options`, `on_cast_error` у условий и `id`, `on_error`, `retry` у действий.

Что форма не умеет показать, она показывает **только для чтения** и сохраняет без изменений:

- условия, если хотя бы одно из них со списком значений (`in`, `between`), с выражением (`value_type: expression`) или
  это вложенная группа: весь блок условий выводится JSON с предупреждением **Часть условий использует списки значений,
  диапазоны или вложенные группы**;
- строки изменения с типами **Сдвиг даты**, **Дописать** / **Удалить из списка**, **По таблице соответствия**,
  **Агрегат по записям**;
- шаг `start_process` со списком `process_ids`;
- все действия, у которых нет панели в редакторе (серые строки с JSON-сводкой).

`trigger_on` сохраняется (форма его не отправляет, и сервер оставляет прежнее значение). Чтобы поменять то, что
показано только для чтения, используйте `PUT /api/processes/{id}`; перед правкой можно сделать копию кнопкой
**Клонировать**.

### Почему в списке «Тип сравнения» нет «Больше», «Между» и «Один из»?

В редакторе нет выбора типа сравнения (`cast`) и поле значения одно, поэтому список показывает только операторы, которые
форма может сохранить:

- с одним значением — **Равен**, **Не равен**, **Включает**, **Не включает**, **Начинается с**, **Заканчивается на**,
  **Изменилось на**, **Изменилось с**;
- без значения — **Пусто**, **Не пусто**, **Данные отсутствуют**, **Данные есть**, **Изменилось**, **Не изменилось**;
  поля значения в такой строке заменяются прочерками, и `value` не отправляется.

Сравнения с `cast` (**Больше**, **Меньше** …), списки (**Один из**, **Содержит любой из** …) и диапазоны (**Между**)
задаются через API — см. [Условия запуска](03-user-guide/triggers-and-conditions.md#операторы). Если такое условие уже
есть в процессе, его оператор остаётся в списке этой строки, а `cast` сохраняется. Типы изменения тоже ограничены теми, у
которых есть поле ввода: **Равен значению**, **Равен переменной**, **Расчёт**, **Шаблон**, **Увеличить на** /
**Уменьшить на** (пустой шаг — 1), **Очистить**.

### Действие «изменение» меняет запись в CRM?

Само по себе — нет. `modify` меняет значение только в памяти процесса. CRM обновляется, если у строки отмечено
**Сохранить в CRM** (`save_to_crm: true`) или есть отдельная строка `save_object`. Отправляются только изменённые поля.
См. [Действия](03-user-guide/actions.md).

### Можно ли в условиях использовать ИЛИ и скобки?

Табличный редактор объединяет все строки по «И». Через API принимается вложенная форма
`{ "logical_operator": "AND" | "OR", "conditions": [...], "groups": [...] }`. Редактор показывает такие условия как
«расширенные» и сохраняет их без изменений. См. [Условия запуска](03-user-guide/triggers-and-conditions.md). Внутри
действий для «если / иначе» есть блок `condition` с несколькими ветками.

### Как запускать процесс только при создании или при удалении записи?

Полем `trigger_on` (через API): `["create"]` — только при создании, `["update"]` — только при изменении, `["delete"]` —
при удалении, `[]` — только вручную. По умолчанию `["create", "update"]`. См.
[Условия запуска → Тип события](03-user-guide/triggers-and-conditions.md#тип-события-и-поле-запускать-при-trigger_on).

### Как сработать только при изменении поля, а не при каждом сохранении?

Операторами **Изменилось**, **Изменилось на**, **Изменилось с**, **Не изменилось**: `object.sales_stage`
**Изменилось на** `Closed Won` срабатывает один раз, при переходе, а не при каждом сохранении выигранной сделки.
Нужен плагин CRM с контрактом 2.0. Старое значение — `object_before.<поле>`. См.
[Условия на изменение поля](03-user-guide/triggers-and-conditions.md#условия-на-изменение-поля).

### Процесс сохраняет запись, и это снова запускает тот же процесс. Как избежать цикла?

Защита от каскадов пока не реализована, поэтому условие процесса, который сохраняет свой `object`, должно стать ложным
после сохранения. Надёжнее всего — оператор **Изменилось** по полю, которое процесс не меняет (или меняет в конечное
состояние): после сохранения CRM не сообщит это поле изменённым. Второй вариант — **Однократный запуск для записи**.
Примеры — рецепты [54](03-user-guide/recipes.md#54-нормализовать-телефон-в-e164-regex_replace-right) и
[56](03-user-guide/recipes.md#56-чистка-контакта-фио-и-e-mail-регулярные-выражения-строки).

### Можно ли в условии использовать поле связанной записи?

Да. Объявите переменную в **Предзагрузке** (например, `v1` — контрагент) и используйте в условии `v1.status`. WPS сначала
проверяет строки по `object.*`, и только если они выполнены, делает предзагрузку и проверяет остальные строки
(«ленивая предзагрузка»).

### Как получить все задачи (сделки, контакты) записи, а не одну?

Предзагрузка загружает одну запись. Для списка используйте действие **Найти записи** (`find_records`): по модулю с
фильтром (`Tasks`, `parent_id equals object.id`, `status not_in [...]`) или по связи (`related_to: {record: object, link:
contacts}`). Результат — переменная-список `{items, count, has_more, ids}`: её читают шаблоны и выражения
(`{{ tasks.count }}`, `sum(pluck(tasks.items, 'amount'))`), а `ids` можно передать в «Связать записи». Список только для
чтения — см. [Действия → Найти записи](03-user-guide/actions.md#найти-записи).

### Можно ли сравнить поле с вычисленным значением, например «больше 80 % лимита»?

Да: `"value_type": "expression"` — правая часть вычисляется выражением (`v1.credit_limit * 0.8`,
`coalesce(v1.limit, 0)`, `add_days(today(), 30)`, `config.min_amount`) и приводится тем же `cast`, что и поле. Для
`between` — пара выражений. Только через API. См.
[Условия запуска → Сравнение с выражением](03-user-guide/triggers-and-conditions.md#сравнение-с-выражением).

### Как задать условие «в ближайшие 30 дней» или «за последние сутки»?

Относительной датой в статическом значении условия с `cast: date` / `datetime`: `today+30d`, `now-24h`,
`["start_of_quarter", "end_of_quarter"]` для `between`. Якоря считаются в `WPS_TIMEZONE`, рабочих дней нет. То же
работает в фильтрах «Найти записи» и агрегата. См.
[Условия запуска → Относительные даты](03-user-guide/triggers-and-conditions.md#относительные-даты).

### Как поменять порог или адрес сразу во всех строках процесса?

Вынесите значение в **константы процесса**: `"constants": { "vip_threshold": 100000, "manager_email": "…" }` в
`definition`, а в строках пишите `config.vip_threshold`. Константы видны в условиях, выражениях, шаблонах и фильтрах,
только для чтения; секреты в них хранить нельзя. Задаются через API; редактор их не показывает, но при сохранении из него сохраняет. См.
[Процессы → Константы процесса](03-user-guide/processes.md#константы-процесса) и рецепт
[58](03-user-guide/recipes.md#58-сегмент-и-скидка-сделки-по-константам-config).

## Выражения и данные

### Как работать с мультисписком (`^a^,^b^`) и списками значений?

В условиях — операторы **Содержит любое из**, **Содержит все из**, **Не содержит ни одного из** с `cast: list`. В
выражениях — функции списков: `to_list(object.tags_c, ',', '^')` разбирает мультисписок, `in('vip', …)` проверяет
элемент, `unique`, `sort`, `without`, `count`, `first`, `pluck`, `where`, `sum` обрабатывают список, а
`join(list, ',', '^')` собирает его обратно в формат CRM. Список, записанный в поле напрямую, сохраняется как
JSON-массив. См. [Списки](03-user-guide/change-types-and-expressions.md#списки) и рецепт
[55](03-user-guide/recipes.md#55-интересы-лида-порядок-и-метка-vip-функции-списков).

### Как почистить строку: телефон, ФИО, e-mail?

Строковыми функциями в **Расчёте**: `trim`, `lower`, `upper`, `title_case`, `replace`, `pad_left`, `translit`, `slug` и
регулярными выражениями `regex_replace(object.phone, '[^0-9+]', '')`, `regex_match`, `regex_extract`. Шаблон пишется
без разделителей, Unicode включён; в JSON обратный слэш удваивается (`'\\d'`). См.
[Регулярные выражения](03-user-guide/change-types-and-expressions.md#регулярные-выражения) и рецепты
[54](03-user-guide/recipes.md#54-нормализовать-телефон-в-e164-regex_replace-right),
[56](03-user-guide/recipes.md#56-чистка-контакта-фио-и-e-mail-регулярные-выражения-строки).

### Как достать значение из JSON — из поля CRM или из ответа внешнего API?

`json_get(источник, '$.путь', 'по умолчанию')` и `json_get_all(источник, '$.items[*].id')` принимают и строку JSON (поле
CRM), и уже разобранный ответ `http_request` (`erp.body`). Путь — JSONPath с фильтрами (`$.items[?(@.qty > 3)]`).
Простые поля ответа можно сразу вынести в `response.extract` шага `http_request` или читать путём `erp.body.data.id`.
См. [JSON](03-user-guide/change-types-and-expressions.md#json) и рецепт
[57](03-user-guide/recipes.md#57-лид-в-erp-разбор-json-ответа-http_request-json_get).

### Как проверить тип значения: число ли это, дата ли?

Функциями `is_number`, `is_numeric_text`, `is_int`, `is_date`, `is_bool`, `is_empty`, `is_list`, `is_object` — они
всегда возвращают `true` / `false` и не роняют шаг. Приведение — `to_number`, `to_int`, `to_bool`, `to_date`,
`to_string`. См. [Проверки и приведение типов](03-user-guide/change-types-and-expressions.md#проверки-и-приведение-типов).

### Как вписать в письмо или уведомление id выполнения, имя процесса, автора изменения?

Системными переменными `sys.*`: `{{ sys.execution_id }}`, `{{ sys.process_name }}`, `{{ sys.process_version }}`,
`{{ sys.trigger }}`, `{{ sys.user_id }}`, `{{ sys.event_type }}`, `{{= join(sys.changed_fields, ', ') }}`,
`{{ sys.now }}`. Они только для чтения и вычисляются при обращении. Полный список — `GET
/api/dictionaries/system-variables` и [Системные переменные](03-user-guide/change-types-and-expressions.md#системные-переменные-и-константы);
пример — рецепт [59](03-user-guide/recipes.md#59-крупная-сделка-уведомление-с-данными-выполнения-sys-config).

### Как посчитать сумму или количество связанных записей?

Типом изменения **Агрегат по записям** (`aggregate`) в `modify` или `set_variable`: `count`, `sum`, `avg`, `min`,
`max` по записям модуля с фильтром или по связи — без поиска и цикла. Если нужен отбор, а фильтра по модулю нет (в
SuiteCRM у сделок нет колонки `account_id`), используйте «Найти записи» по связи и `sum(pluck(…))` или накопитель в
цикле. См. [Агрегат по записям](03-user-guide/change-types-and-expressions.md#агрегат-по-записям).

### Как изменить каждую найденную запись?

Если всем записям нужны одни и те же поля (статус, ответственный, дата) — действием **Изменить записи списка**
(`update_records`): один шаг, неизменённые записи не отправляются, см.
[Действия → Изменить записи списка](03-user-guide/actions.md#изменить-записи-списка). Если для каждой записи нужны
разные действия — блоком **Цикл** (`foreach`): `"source": "deals.items", "as": "deal"`, в теле — `modify deal.…` и обязательно
`save_object` с `target: "deal"` (элемент — копия, без сохранения изменения в CRM не попадут; такие итерации видны в
`unsaved_items`). Отбор элементов — `where`, продолжение после ошибки элемента — `on_item_error: continue`. См.
[Действия → Цикл](03-user-guide/actions.md#цикл-для-каждого-элемента).

## Письма, уведомления, внешние системы

### Как отправить письмо и где посмотреть его на тестовом стенде?

Действием **Отправить письмо** (`send_email`): получатели — адреса, шаблоны или пути к полям (`owner.email1`), тема и
тело — шаблоны, по желанию — запись истории письма в CRM. Транспорт — `MAILER_DSN` или секрет `smtp_dsn`. На стенде из
`docker-compose.yml` все письма ловит Mailpit: `http://localhost:8025`. Проверить настройки почты без процесса —
`POST /api/mail/test` (admin). Вложений и шаблонов писем CRM пока нет. См.
[Действия → Отправить письмо](03-user-guide/actions.md#отправить-письмо).

### Как отправить уведомление в колокольчик CRM, Telegram или Slack?

Действием **Уведомление** (`notify`): один шаг, несколько каналов — `crm_alert` (запись `Alerts`, видна в колокольчике
SuiteCRM 7 и 8), `telegram` (бот, секрет `telegram_bot`), `slack` и `teams` (вебхук, секрет `webhook_url`). Повтор шага
не дублирует уже доставленное. Проверить канал без процесса — `POST /api/notify/test`. Письма клиентам — действием
«Отправить письмо». См. [Действия → Уведомление](03-user-guide/actions.md#уведомление).

### Как вызвать внешний API или вебхук?

Действием **HTTP-запрос** (`http_request`): метод, URL (схема и хост — литералом), query, заголовки и тело — шаблоны,
авторизация — только из секретов (`bearer`, `basic`, `api_key`, OAuth2 client credentials). Ответ кладётся в
переменную (`var`) и разбирается JSONPath. Адрес проверяет SSRF-защита: внутренние адреса по умолчанию запрещены. См.
[Действия → HTTP-запрос](03-user-guide/actions.md#http-запрос).

### Где хранить пароли и токены внешних систем?

В **секретах** WPS (`/api/secrets`, создаёт администратор): значение шифруется ключом `WPS_SECRETS_KEY`, ни один ответ
API его не возвращает, в аудите и логах оно маскируется. Процесс ссылается на секрет `secret://имя` только в полях
учётных данных (`transport`, `auth`, `connection`, `url` вебхука). Экрана секретов в интерфейсе нет. См.
[Секреты](03-user-guide/secrets.md).

### Письмо или запрос может уйти дважды после сбоя?

Нет, если не настроено иначе. Каждый внешний вызов записывается в журнал побочных эффектов: шаг, повторённый после
падения воркера, берёт ответ из журнала (`replayed: true`). Если воркер упал посреди отправки и исход неизвестен, при
`delivery: at_most_once` (по умолчанию для писем, `POST` и уведомлений) шаг завершается `UNKNOWN_OUTCOME` без повтора;
`at_least_once` — повторяет. Журнал выполнения — `GET /api/executions/{id}/side-effects`. См.
[Надёжность → Побочные эффекты](04-operations/reliability.md#побочные-эффекты-и-повторы).

### Как распределять лиды или обращения между сотрудниками?

Действием **Назначить ответственного** (`assign`): `round_robin` — по кругу, `least_busy` — наименее загруженному,
`random`, `manager` — руководителю текущего ответственного, `user` — конкретному. Пул — список пользователей или группа
безопасности CRM; неактивные и сотрудники в отпуске пропускаются. Повтор шага после ошибки не сдвигает очередь. Сброс
очереди — `DEL assign:rr:<queue_key>` в redis-data. См.
[Действия → Назначить ответственного](03-user-guide/actions.md#назначить-ответственного).

## Выполнение, ожидание, ошибки

### Как сделать «через 2 дня» или «за 30 дней до окончания договора»?

Шагом **Пауза** (`delay`): `"mode": "duration", "duration": "2d"` или `"mode": "until", "until": "object.end_date",
"offset": "-P30D", "time": "09:00"`. Длинная пауза паркует выполнение в PostgreSQL (статус **Ожидает**), воркер
свободен, ожидание переживает перезапуск. Короткие паузы (до `WAIT_INLINE_MAX_SECONDS`, 5 с) ждут в памяти. См.
[Действия → Пауза](03-user-guide/actions.md#пауза-delay).

### Что будет с ожидающими выполнениями, если изменить, выключить или удалить процесс?

- **Изменить** — ожидающее выполнение продолжит со своей версией определения и своими константами.
- **Выключить** (неактивен) — ожидание не останавливается: выполнение проснётся и доработает.
- **Удалить** — без `?force=true` сервер ответит `409 PROCESS_HAS_WAITING_EXECUTIONS`; с `force=true` (кнопка
  **Удалить** в интерфейсе этот параметр не передаёт — используйте API) ожидающие выполнения получают статус
  **Отменено**.

Найти ожидающие: `GET /api/executions?status=waiting`. См.
[Выполнения и аудит → Ожидающие выполнения](03-user-guide/executions-and-audit.md#ожидающие-выполнения).

### Как продолжить процесс, если один шаг упал?

Полем шага `on_error`: `"continue"` — перейти к следующему шагу, `{"goto": "<id>"}` — перейти вперёд к шагу с `id`
(например, к шагу «создать задачу на ручную проверку»), `"stop"` — по умолчанию. Повторы временных ошибок — профиль
`retry` шага. Выполнение с обработанными ошибками завершается **Завершено**, число ошибок — `handled_errors`, текст
последней — `sys.last_error`. См. [Действия → Ошибки шага](03-user-guide/actions.md#ошибки-шага-on_error-и-повторы).

### Как найти все упавшие или ожидающие выполнения?

В интерфейсе журнал есть у каждого процесса (фильтр **Статус**). По всем процессам — через API:
`GET /api/executions?status=failed&date_from=…` или `?status=waiting&due_before=…`. Для оповещения о росте ошибок —
метрика `wps_executions_failed_total` в Prometheus. См. [Выполнения и аудит](03-user-guide/executions-and-audit.md).

### На одно событие подходят несколько процессов. В каком порядке они выполняются?

По возрастанию `priority`: меньшее значение выполняется раньше. Каждый процесс получает свою свежую копию события, поэтому
переменные одного процесса не видны другому. Ошибка в одном процессе не останавливает остальные.

### Ведомый процесс ждёт родителя, а родитель — ведомый?

Родитель не ждёт. `start_process` запускает ведомый процесс асинхронно и переходит к следующему шагу. Ведомый процесс
получает событие родителя и все его переменные на момент запуска, свои константы и свои `sys.*` (`sys.depth` на 1
больше, `sys.parent_execution_id` — родитель). См. [Ведомые процессы](03-user-guide/subprocesses.md).

### Может ли процесс запустить сам себя или образовать цикл А → Б → А?

Нет. Сохранение отклоняется с сообщением «процесс не может запускать сам себя» или с `422 CYCLE_DETECTED` и путём цикла.
Во время выполнения глубина вложенности дополнительно ограничена `MAX_CHILD_DEPTH` (по умолчанию 10).

### Что будет с идущими выполнениями, если я изменю процесс?

Каждое сохранение увеличивает `version`. Уже начатые выполнения доходят до конца с тем определением, с которым стартовали:
оно хранится в состоянии выполнения. Страница выполнения показывает использованную версию. Новые события сразу
используют новую версию: при сохранении кэш процессов сбрасывается.

## Надёжность

### Что если CRM недоступна?

Временные ошибки (таймаут, ошибка соединения, HTTP 5xx) повторяются `ACTION_RETRY_MAX` раз (3) с экспоненциальной
задержкой: по умолчанию 1 с, 2 с, 4 с; профиль `retry` шага меняет число попыток и задержки. Во время ожидания статус
выполнения — «Повтор»; задержка длиннее `WAIT_INLINE_MAX_SECONDS` (5 с, например `retry.max_delay: 10m`) паркует
выполнение — статус «Ожидает», воркер свободен, ожидание переживает перезапуск. После последней попытки шаг и
выполнение получают статус «Ошибка», оставшиеся шаги — «Пропущен». Ответ CRM 4xx не повторяется.
См. [Надёжность](04-operations/reliability.md).

### Может ли событие обработаться дважды?

Стрим обрабатывается по схеме «как минимум один раз», но у каждой пары (событие, процесс) есть ключ идемпотентности.
Поэтому повторно доставленное событие процесс заново не запускает. Чтобы процесс выполнялся не больше одного раза на
**запись** CRM (а не на событие), включите **Однократный запуск для записи**.

### Удаляется ли история выполнений?

Автоматической очистки таблиц `executions` и `execution_actions` в WPS нет: аудит хранится, пока вы не удалите его в базе.
Истекает только состояние завершённых выполнений в Redis — через `EXECUTION_FINISHED_TTL_SECONDS` (3600 с) — и записи
журнала побочных эффектов старше `SIDE_EFFECTS_RETENTION_DAYS`. Удаление процесса мягкое, поэтому его аудит остаётся
целостным.

### Как проверить, что сервис жив?

`GET /api/health` (без входа): `status: ok` или `degraded` с проверкой PostgreSQL и обоих Redis и состоянием стрима
(`lag`, `pending`, `consumers`). Метрики Prometheus — `GET /metrics`: события, выполнения, письма, уведомления, HTTP,
ожидания. См. [Мониторинг](04-operations/monitoring.md).

## Администрирование

### Кто что может?

`admin` — всё, включая удаление процессов, секреты и управление пользователями. `editor` — создание, редактирование,
клонирование и ручной запуск процессов, сброс однократных запусков, просмотр списка секретов. `viewer` — только
просмотр. См. [Пользователи и роли](03-user-guide/users-and-roles.md).

### Почему не удаляется процесс?

Удалять процессы может только `admin`. Ведомый процесс, который другой процесс запускает через `start_process`, удалить
нельзя (`409 PROCESS_IN_USE`) — сначала уберите ссылку на него. Процесс с ожидающими выполнениями удаляется только через
API с `?force=true` (`409 PROCESS_HAS_WAITING_EXECUTIONS`).

### Список типов объектов пуст или устарел.

Справочник модулей кэшируется в Redis на `DICT_CACHE_TTL` (300 с). Нажмите **Обновить список модулей из CRM** рядом с
полем. Если список всё равно пуст, проверьте `MOCK_SERVICE_URL` и `CRM_API_BASE_URL`, см.
[Интеграция с CRM](04-operations/crm-integration.md).

### Как переключить язык интерфейса?

Через меню языка в шапке или на странице входа либо параметром `?lang=ru` / `?lang=en` в адресе. Выбор запоминается в
браузере. Сообщения, которые приходят с сервера (подробности ошибок валидации), — на английском, а подписи справочников
(операторы, типы изменений, кроме базовых) — на русском при любом языке интерфейса.

### Как добавить новое действие, оператор или функцию?

Это PHP-классы, которые регистрируются в `Wps\Kernel\Container`. Пошаговые инструкции с полными примерами — в
[Руководстве разработчика](07-developer-guide/extending/new-action-type.md).
