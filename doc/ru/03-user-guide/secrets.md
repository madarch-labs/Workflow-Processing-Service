# Секреты

Как администратор хранит учётные данные внешних систем в WPS и как процесс ссылается на них, не видя значения.

<!-- lang-switch -->
[🇬🇧 English](../../en/03-user-guide/secrets.md) | 🇷🇺 Русский
<!-- /lang-switch -->

## Зачем

Внешним действиям нужны учётные данные: пароль SMTP, токен API, ключ Telegram-бота, client secret OAuth2. Класть их в
определение процесса нельзя: определение видят все роли, оно попадает в аудит и в выгрузки. Поэтому значение хранится в
WPS отдельно и зашифрованно, а процесс содержит только ссылку `secret://name`.

- Администратор заводит секрет и при необходимости меняет его значение — процессы править не нужно.
- Редактор видит имя, вид и маску секрета и ссылается на него в процессе, но значение не видит.
- В аудите выполнения вместо значения — `***`.

Как устроено шифрование, ключ и его ротация — [Безопасность → Секреты процессов](../04-operations/security.md#секреты-процессов).
Интерфейса для секретов пока нет: они управляются через API (`/api/secrets`, см.
[Справочник API](../06-api-reference/endpoints.md#секреты)).

## Секрет

| Поле | Описание |
|---|---|
| `name` | Имя для ссылок: `^[a-z][a-z0-9_]{1,63}$`, уникально. Переименовать нельзя — процессы ссылаются по имени |
| `kind` | Вид (таблица ниже), задаётся при создании и не меняется. По умолчанию `generic` |
| `value` | Значение: строка или объект (для составных видов). Только на запись — никто его не прочитает |
| `description` | Свободный текст |
| `allowed_hosts` | Необязательный список хостов, на которые секрет можно отправлять (`api.example.com`, `*.example.com`, с портом или без). Действия, отправляющие секреты во внешние системы, проверяют этот список — так редактор не сможет отправить токен на свой сервер |
| `mask` | Маска для списка: `****` + 4 последних символа для значений от 12 символов, иначе `********` |
| `version` | Растёт при каждой смене значения |

Виды (справочник `GET /api/dictionaries/secret-kinds`):

| `kind` | Значение | Проверка |
|---|---|---|
| `generic` | строка | не короче 4 символов |
| `smtp_dsn` | строка DSN, например `smtp://user:pass@smtp.example.com:587` | формат DSN; используется полем `transport` действия [`send_email`](actions.md#отправить-письмо) |
| `basic_auth` | `{ "username", "password" }` | оба поля обязательны; `username` не секретен и виден в маске |
| `bearer` | строка-токен | не короче 4 символов |
| `api_key` | строка | не короче 4 символов |
| `oauth2_client` | `{ "token_url", "client_id", "client_secret", "scope"? }` | `token_url` — только `https://`; `token_url`, `client_id`, `scope` видны в маске |
| `webhook_url` | строка — URL `http(s)://` | корректный URL; `connection` каналов `slack` и `teams` действия [`notify`](actions.md#уведомление) |
| `telegram_bot` | строка — токен бота | не короче 4 символов; `connection` канала `telegram` действия [`notify`](actions.md#уведомление) (токен попадает в путь URL, поэтому URL маскируется целиком) |

Секретные строки короче 4 символов не принимаются: такие значения нельзя надёжно вырезать из текста аудита.

Создание (только `admin`):

```bash
curl -s -X POST http://localhost:9501/api/secrets -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"erp_token","kind":"bearer","value":"tok-0123456789abcdef","description":"ERP API"}'
```

```json
{"success":true,"data":{"name":"erp_token","kind":"bearer","description":"ERP API","mask":"****cdef","allowed_hosts":[],
 "version":1,"created_at":"2026-10-19T19:29:33Z","updated_at":"2026-10-19T19:29:33Z","last_used_at":null},"error":null}
```

## Ссылка из процесса

| Форма | Что подставляется |
|---|---|
| `secret://erp_token` | значение целиком (строка или объект составного секрета) |
| `secret://erp_oauth.client_id` | одно поле составного секрета |

Ссылка — это **всё** значение поля учётных данных действия. Такие поля объявляют действия, которые обращаются к
внешним системам (отправка письма, HTTP-запрос, уведомления), например:

```json
{ "type": "http_request", "url": "https://erp.example.com/api/orders",
  "auth": { "type": "bearer", "token": "secret://erp_token" } }
```

Значение подставляется в памяти в момент шага и никуда не записывается: ни в переменные процесса, ни в Redis, ни в
аудит.

Где ссылка запрещена — в шаблонах, значениях `modify` (`value`, `expression`), полях `field` / `target` и в условиях.
Там секрет оказался бы в данных процесса, поэтому сохранение процесса отклоняется.

## Ошибки

| Ситуация | Ответ |
|---|---|
| Ссылка на несуществующий секрет | `422`, `definition.actions[2].auth.token: Secret "erp_token" does not exist` |
| Ссылка в шаблоне, значении шага или условии | `422`, `… : Secrets can only be used in credential fields` |
| Неверная форма ссылки (`secret://Bad`) | `422`, `Invalid secret reference (expected secret://name or secret://name.field)` |
| Секрет удалён или ключ не подходит во время выполнения | шаг `failed`: `Secret "erp_token" not found` / `Secret "erp_token" has no field "x"` |
| Удаление используемого секрета | `409 SECRET_IN_USE` со списком использований `usages: [{process_id, process_name, path}]` |
| Секрет с таким именем уже есть | `409 SECRET_EXISTS` |
| Ключ хранилища не задан | `503 SECRETS_KEY_NOT_CONFIGURED` |

`GET /api/secrets/{name}` показывает, где секрет используется (`usages`) — по ним видно, какие процессы затронет смена
значения. Удалить секрет можно, только когда ссылок в неудалённых процессах не осталось.

## Смена значения

```bash
curl -s -X PUT http://localhost:9501/api/secrets/erp_token -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"value":"tok-new-0123456789"}'
```

`version` увеличивается на 1, маска пересчитывается. Воркеры кэшируют расшифрованное значение в памяти на
`SECRETS_CACHE_TTL` секунд (по умолчанию 60) — новое значение начинает использоваться в пределах этого срока. Имя и вид
поменять нельзя: создайте новый секрет и переключите на него процессы.
