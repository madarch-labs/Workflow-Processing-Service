# Ведомые процессы

Как разбить сценарий на родительский и ведомые процессы, что получает ведомый процесс, как он запускается и
выполняется, какие ограничения и ошибки бывают.

## Когда нужен ведомый процесс

**Ведомый процесс** (`is_child: true`) никогда не запускается событием CRM напрямую: при обработке события подбираются
только активные **процессы верхнего уровня**. Ведомый процесс выполняется, только когда его запускает другой процесс
действием **Запустить следующий процесс** (`start_process`). Ведомые процессы удобны, чтобы:

- использовать одну цепочку действий из нескольких родительских процессов;
- выполнять независимые ветки параллельно (каждый ведомый процесс работает в своей корутине);
- не перегружать длинный родительский процесс;
- запускать отдельное выполнение со своим журналом на каждый элемент списка — `start_process` внутри
  [цикла `foreach`](actions.md#цикл-для-каждого-элемента).

Когда ведомый процесс **не подходит**:

| Задача | Что использовать вместо |
|---|---|
| Получить результат ведомого процесса и продолжить с ним в родителе | Ничего: родитель ведомый процесс не ждёт и его переменные не получает. Оставьте шаги в родительском процессе |
| Выбрать одну из нескольких веток действий | Блок [`condition`](actions.md#условие-если--иначе) в том же процессе |
| Одинаково изменить поля у всех найденных записей | [`update_records`](actions.md#изменить-записи-списка) |
| Остановить всё, если ведомый процесс упал | Невозможно: ошибка ведомого процесса на родителя не влияет |

## Создание ведомого процесса

1. Откройте **Создать процесс**.
2. В поле **Тип процесса** выберите **Ведомый процесс**.
3. Выберите **Тип объекта (object.type)**. Для ведомого процесса это справочная информация: он работает с объектом
   события родителя, какого бы типа тот ни был.
4. Настройте условия, предзагрузку и действия как обычно и сохраните процесс.

Через API это поле `"is_child": true` тела `POST /api/processes` ([Справочник API](../06-api-reference/endpoints.md)).

В ведомом процессе можно ссылаться на переменные, которые в нём не объявлены (например, `v1.name`, загруженную
родителем): валидатор разрешает неизвестные переменные, потому что ведомый процесс наследует все переменные родителя.
Обратная сторона — опечатку в имени такой переменной валидатор не поймает: при выполнении она будет просто не найдена
(пустое значение в шаблоне, ложное условие).

Что из настроек процесса действует для ведомого процесса:

| Настройка | Для ведомого процесса |
|---|---|
| `is_active` | Учитывается: неактивный ведомый процесс не запускается (шаг родителя при этом успешен, см. ниже) |
| `trigger_on` | **Не учитывается**: ведомый процесс запускается родителем при любом типе события |
| `run_once` | Учитывается: отметка ставится на запись из события родителя (`object.id`), повторный запуск для той же записи пропускается |
| `priority` | Не влияет: порядок ведомых процессов задаётся порядком шагов `start_process` |
| `definition.constants` | Свои: ведомый процесс читает `config.*` **своего** определения, а не родительского |

В карточке ведомого процесса есть поле **Запускается из** со ссылками на все процессы, которые его запускают. Пока
такие ссылки есть, процесс нельзя сделать процессом верхнего уровня (`is_child: false`): сохранение вернёт
`422`, `is_child: The process is started by other processes (Родитель) and must stay a child process`.

## Запуск ведомого процесса из родительского

1. Откройте родительский процесс на редактирование.
2. В **Блоке 2. Действия** раскройте **Запустить следующий процесс**.
3. Нажмите **Добавить процесс** и выберите ведомый процесс в списке **Выберите ведомый процесс**. В списке только
   процессы с типом **Ведомый процесс**, неактивные помечены **неактивен**. Кнопка обновления перезагружает список
   (**Обновить список ведомых процессов**), ссылка **открыть** открывает выбранный процесс.
4. Сохраните родительский процесс.

![Строка «Запустить следующий процесс» с ведомым процессом #4](../../images/screenshots/ru/08-process-edit-start-process.png)

*Родительский процесс #6: два условия по «И» и одна строка запуска следующего процесса.*

В JSON действие хранится так:

```json
{ "type": "start_process", "process_id": 4 }
```

или, если в одном шаге запускается несколько процессов:

```json
{ "type": "start_process", "process_ids": [4, 7] }
```

`4` и `7` здесь — id **ваших** ведомых процессов (число после `#` в карточке процесса).

Редактор ставит строки **Запустить следующий процесс** в конец списка действий. Через API шаг `start_process` можно
поставить в любое место: между другими действиями, в ветку [условия](actions.md#условие-если--иначе), в тело
[цикла](actions.md#цикл-для-каждого-элемента).

### Поля действия `start_process`

| Поле | Тип | Обязательно | По умолчанию | Описание |
|---|---|---|---|---|
| `type` | строка | да | — | `start_process` |
| `process_id` | целое (или строка из цифр) | `process_id` или `process_ids` | — | id одного ведомого процесса |
| `process_ids` | список целых | `process_id` или `process_ids` | — | Несколько ведомых процессов; запускаются в порядке списка, повторы id убираются. Если заданы оба поля, используется `process_ids` |
| `id`, `name` | строка | нет | — | Общие поля шага: ссылка для `goto` и подпись в аудите ([Поля шага](actions.md#вложенные-блоки-и-поля-шага)) |
| `on_error`, `retry` | | нет | `stop`, глобальный профиль | [Ошибки шага](actions.md#ошибки-шага-on_error-и-повторы) |

Поле `delivery` у `start_process` не поддерживается (`Action "start_process" does not support "delivery"`):
повторный запуск защищён ключом идемпотентности (см. [Как он выполняется](#как-он-выполняется)).

## Что получает ведомый процесс

| | Поведение |
|---|---|
| Событие | То же событие, что у родителя (`event_id`, тип события, изменённые поля). |
| `object` | Значения **после** изменений родителя, сделанных до шага `start_process`, — в том числе ещё не сохранённых в CRM. |
| `object_before` | Те же старые значения, что у родителя (только чтение). |
| Переменные | **Копия** всех переменных родителя на момент шага: предзагрузки (`v1`), созданные `modify` (`task`), локальные `set_variable` (`calc`), списки `find_records`, ответы `http_request`, а внутри цикла — текущий элемент и данные итерации. Модули переменных тоже переходят: `save_object` в ведомом процессе знает модуль переменной родителя. |
| Изменения переменных | Ведомый процесс работает со своей копией: его изменения не видны родителю, а изменения родителя после запуска не видны ведомому процессу. |
| Несохранённые изменения | Не наследуются: в ведомом процессе изменённых полей нет, поэтому `save_object` в нём отправляет только поля, изменённые самим ведомым процессом. |
| `config.*` | Константы **ведомого** процесса. |
| `sys.*` | Свои значения выполнения (таблица ниже). |
| Источник запуска | `child` (в журнале — **Дочерний**), `parent_execution_id` указывает на выполнение родителя. |
| Условия | Проверяются собственные условия ведомого процесса; если они не выполнены, он не запускается. |
| Предзагрузка | Выполняется своя, как у любого процесса. Имена предзагрузки не должны совпадать с переменными, которые придут от родителя, иначе значение родителя будет перезаписано. |
| Однократный запуск | Применяется к записи из события родителя (`object.id`). |

### Системные переменные в ведомом процессе

| Переменная | Значение в ведомом процессе |
|---|---|
| `sys.execution_id` | id выполнения ведомого процесса |
| `sys.parent_execution_id` | id выполнения родителя (у процессов верхнего уровня — пусто) |
| `sys.trigger` | `child` |
| `sys.depth` | глубина вложенности: у родителя верхнего уровня `0`, у его ведомого процесса `1`, у следующего — `2` |
| `sys.process_id`, `sys.process_name`, `sys.process_version` | данные **ведомого** процесса |
| `sys.started_at`, `sys.now` | время старта и текущее время ведомого выполнения |
| `sys.event_id`, `sys.event_type`, `sys.changed_fields`, `sys.module`, `sys.record_id`, `sys.user_id` | из события родителя |
| `sys.last_error`, `sys.errors_count` | значения родителя на момент запуска: если родитель обработал ошибку (`on_error`) до шага `start_process`, ведомый процесс видит её в `sys.last_error`, и его `sys.errors_count` (и `handled_errors` выполнения) начинается с числа ошибок родителя |

Полная таблица `sys.*` — в разделе [Системные переменные и константы](change-types-and-expressions.md#системные-переменные-и-константы).

## Как он выполняется

1. **Проверка списка.** Шаг сначала проверяет все id: процесс существует и он ведомый. Если хотя бы один не прошёл,
   шаг завершается ошибкой и **ни один** процесс из списка не запускается.
2. **Неактивный ведомый процесс пропускается.** Шаг остаётся успешным, а в его результате у процесса указано
   `"status": "skipped", "reason": "Process is inactive"`.
3. **Асинхронный запуск.** Каждый ведомый процесс запускается в отдельной корутине. Родитель не ждёт ведомый процесс:
   шаг `start_process` завершается сразу после запуска (статус `started` значит «передан на выполнение», а не
   «выполнен»), и родитель переходит к следующему действию.
4. **Условия и однократный запуск** проверяются уже в ведомом выполнении. Если условия не выполнены, выполнение не
   создаётся, а в результате шага родителя всё равно `started`.
5. **Независимость.** Ошибка, пауза или `stop_process` ведомого процесса не влияют на родителя; ошибка или остановка
   родителя после запуска не останавливает ведомый процесс.
6. **Один раз на шаг.** Ключ запуска — «выполнение родителя × шаг × процесс». Если шаг родителя выполняется повторно
   после восстановления от сбоя, тот же ведомый процесс второй раз не запускается. В цикле у каждой итерации свой шаг,
   поэтому `start_process` в теле `foreach` запускает по ведомому выполнению на элемент.
7. **Пауза в родителе.** Шаг `start_process` после [паузы](actions.md#пауза-delay) запускает ведомый процесс после
   пробуждения родителя; ведомый процесс получает переменные на этот момент.

### Ограничение глубины

Цепочка «родитель → ведомый → следующий ведомый …» ограничена параметром `MAX_CHILD_DEPTH` (по умолчанию 10, см.
[Конфигурация](../04-operations/configuration.md)). Глубина ведомого выполнения — `sys.depth`. Шаг `start_process`
в выполнении с глубиной `MAX_CHILD_DEPTH` завершается ошибкой `Maximum child process depth (10) exceeded` (без
повторов). Защита нужна на случай цепочек, которые не ловит проверка циклов при сохранении, — например, процесс,
изменённый в обход валидации.

### Результат шага и журнал

`request_data` шага: `{"process_ids": [4, 7]}` (после удаления повторов). `result_data`:

```json
{
  "children": [
    { "process_id": 18, "name": "Inactive child", "status": "skipped", "reason": "Process is inactive" },
    { "process_id": 16, "name": "Notify manager", "status": "started" }
  ]
}
```

На странице выполнения родителя ведомые процессы перечислены в таблице **Дочерние выполнения**
(`children` ответа `GET /api/executions/{id}`). Нажмите на id, чтобы открыть выполнение ведомого процесса. У ведомого
выполнения `trigger = child` и `parent_execution_id` — id родителя.

## Правила проверки

| Ситуация | Результат при сохранении |
|---|---|
| Нет ни `process_id`, ни `process_ids`, или список пуст | `422 VALIDATION_ERROR`: `Child process is required` (`…process_id` / `…process_ids`) |
| id не целое число | `422 VALIDATION_ERROR`: `Process id must be an integer` |
| Выбранный процесс не ведомый | `422 VALIDATION_ERROR`: `Process 1 "…" is not a child process` |
| Процесса не существует | `422 VALIDATION_ERROR`: `Process 42 not found` |
| Процесс запускает сам себя | `422 VALIDATION_ERROR`: `A process cannot start itself` |
| Цикл запуска, например A → B → A | `422 CYCLE_DETECTED`, в интерфейсе — **Обнаружен цикл запуска процессов** и цепочка процессов |
| У шага задано `delivery` | `422 VALIDATION_ERROR`: `Action "start_process" does not support "delivery"` |
| Ведомый процесс, на который есть ссылки, переводится в верхний уровень | `422 VALIDATION_ERROR`: `is_child: The process is started by other processes (…) and must stay a child process` |
| Удаление ведомого процесса, на который есть ссылки | `409 PROCESS_IN_USE`: `The process is started by other processes`, в `details` — список родителей `[{id, name}]`; в интерфейсе — **Процесс используется другими процессами (start_process) и не может быть удалён** |

Цикл проверяется при сохранении процесса, который уже существует: от его новых ведомых процессов обходятся связи
`start_process` всех процессов; если обход возвращается к сохраняемому процессу — это цикл. Пример ошибки:

```json
{
  "code": "CYCLE_DETECTED",
  "message": "Process launch cycle detected: Cycle A → Cycle B → Cycle A",
  "details": { "path": [ { "id": 16, "name": "Cycle A" }, { "id": 17, "name": "Cycle B" }, { "id": 16, "name": "Cycle A" } ] }
}
```

### Ошибки выполнения

| `error_message` шага | Причина |
|---|---|
| `Maximum child process depth (10) exceeded` | Превышена глубина `MAX_CHILD_DEPTH` |
| `Child process 42 not found` | Защитная проверка: процесса с таким id нет (удалён в обход проверки ссылок) |
| `Process 42 "…" is not a child process` | Защитная проверка: процесс уже не ведомый (изменён в обход проверки ссылок) |

Эти ошибки не повторяются; дальше действует `on_error` шага. При обычной работе через API и редактор две последние
ситуации не возникают: удалить ведомый процесс или сделать его процессом верхнего уровня, пока на него ссылаются, нельзя.

## Пример: задача ответственному в ведомом процессе

Родительский процесс по новым лидам вычисляет приоритет в локальной переменной `calc` и запускает ведомый процесс.
Ведомый процесс создаёт задачу ответственному лида: он читает `object` и `calc` родителя, а
`sys.parent_execution_id` пишет в описание задачи для связи с выполнением родителя.

Ведомый процесс (id, например, `4`):

```json
{
  "name": "Задача ответственному по лиду",
  "object_type": "Leads",
  "is_child": true,
  "is_active": true,
  "definition": {
    "conditions": [ { "field": "object.assigned_user_id", "operator": "is_not_empty" } ],
    "actions": [
      { "type": "modify", "target": "task.name", "change_type": "template",
        "value": "Связаться: {{ object.first_name }} {{ object.last_name }}" },
      { "type": "modify", "target": "task.description", "change_type": "template",
        "value": "Источник: {{ object.lead_source | default:'—' }}. Запущено выполнением {{ sys.parent_execution_id }}" },
      { "type": "modify", "target": "task.priority", "change_type": "set_from_variable", "value": "calc.priority" },
      { "type": "modify", "target": "task.date_due", "change_type": "date_shift", "base": "today", "shift": "+1 day", "set_time": "18:00" },
      { "type": "modify", "target": "task.parent_type", "change_type": "set_value", "value": "Leads" },
      { "type": "modify", "target": "task.parent_id", "change_type": "set_from_variable", "value": "object.id" },
      { "type": "modify", "target": "task.assigned_user_id", "change_type": "set_from_variable", "value": "object.assigned_user_id" },
      { "type": "save_object", "target": "task", "module": "Tasks" }
    ]
  }
}
```

Родительский процесс:

```json
{
  "name": "Новый лид: приоритет и задача",
  "object_type": "Leads",
  "trigger_on": ["create"],
  "definition": {
    "actions": [
      { "type": "set_variable", "target": "calc.priority", "change_type": "calculate",
        "value": "if(object.lead_source == 'Web Site', 'High', 'Medium')" },
      { "id": "start_task", "type": "start_process", "process_id": 4 }
    ]
  }
}
```

Лид с источником `Web Site` и ответственным получает задачу «Связаться: Анна Петрова» с приоритетом `High` на завтра
18:00. Лид без ответственного: шаг родителя `start_process` успешен (`started`), но условия ведомого процесса не
выполнены, и ведомое выполнение не создаётся.

### Ведомый процесс на каждый элемент списка

```json
{
  "object_type": "Accounts",
  "trigger_on": ["update"],
  "definition": {
    "conditions": [ { "field": "object.account_type", "operator": "changed_to", "value": "Customer" } ],
    "actions": [
      { "type": "find_records", "var": "contacts", "related_to": { "record": "object", "link": "contacts" },
        "fields": ["first_name", "last_name", "email1"] },
      { "type": "foreach", "source": "contacts.items", "as": "contact", "actions": [
        { "type": "start_process", "process_id": 7 }
      ] }
    ]
  }
}
```

Ведомый процесс `7` выполняется отдельно для каждого контакта и видит текущий контакт в переменной `contact`
(`{{ contact.email1 }}`), а номер итерации — в `contact_loop.number`. Ошибка в одном ведомом выполнении не мешает
остальным.

> **Примечание**
> Ведомый процесс можно запустить вручную из его карточки, как любой другой процесс (см. [Ручной запуск и сброс](manual-run-and-reset.md)).
> В этом случае родителя нет: источник запуска — `manual`, унаследованных переменных нет, `sys.parent_execution_id`
> пуст, а `sys.depth` равен `0`.
