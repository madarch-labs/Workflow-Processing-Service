# Архитектурные решения

Ключевые проектные решения WPS в коротком формате ADR: контекст, решение, последствия. Обоснования взяты из комментариев в коде, `md/doc/maiInfo.md` (пронумерованные ответы заказчика) и планов в `md/`.

## ADR-1. PHP + Swoole + SwooleApp

**Контекст.** По заданию сервис пишется на PHP на Swoole и фреймворке SwooleApp (`md/doc/maiInfo.md`, вводная часть).
Сервис должен непрерывно читать стрим событий, обращаться к медленному внешнему API и одновременно обслуживать REST API;
ожидаемая нагрузка — до сотни событий в секунду по типу объекта и сотни активных процессов на тип (ответ №21).

**Решение.** Долгоживущий HTTP-сервер Swoole на SwooleApp (`sidalex/swoole-app` из Packagist): контроллеры по
атрибуту, глобальные middleware, циклические задачи и контейнер состояния из `config/config.json`. `SWOOLE_HOOK_ALL`
делает PDO, phpredis и сокеты совместимыми с корутинами; CRM вызывается корутинным HTTP-клиентом.

**Последствия.** Один воркер обрабатывает много событий и запросов одновременно, ожидание CRM или паузы перед повтором
не занимает поток. Сервисы и соединения живут в памяти, поэтому после fork каждому воркеру нужны свои экземпляры
(см. ADR-10). Изменения кода требуют перезапуска — так же выкатываются новые типы действий (ответы №25, №26).

## ADR-2. Redis Stream с группой потребителей как шина событий

**Контекст.** CRM публикует каждое сохранение объекта (ответ №2). Обработка должна переживать падения и обрабатывать
каждое событие хотя бы один раз (ответ №22); события, под которые не подошёл ни один процесс, просто считаются
прочитанными (ответ №23).

**Решение.** Стрим `crm_events`, группа `wps_workers`, по потребителю на каждый HTTP-воркер. Сообщение подтверждается
только после обработки всех его процессов. Неподтверждённые сообщения забирает `RecoveryJob` через `XAUTOCLAIM`;
некорректные сообщения и сообщения, доставленные больше пяти раз, уходят в `crm_events:dlq`.

**Последствия.** Горизонтальное масштабирование добавлением воркеров или экземпляров backend в ту же группу. Доставка —
«хотя бы один раз», поэтому обработка должна быть идемпотентной (ADR-7). «Отравленное» сообщение не может навсегда
заблокировать стрим.

## ADR-3. PostgreSQL для консистентных данных, отдельный Redis для кэша и состояния

**Контекст.** Заказчик предложил PostgreSQL как консистентное хранилище и Redis для кэша и временных данных —
**отдельный экземпляр, не тот, что используется как шина** (ответ №4).

**Решение.** В PostgreSQL хранятся пользователи, процессы (определение в JSONB), выполнения, аудит шагов и отметки
однократного запуска. В `redis-data` — кэши процессов и модулей, контекст выполнений, блокировки и ключи
идемпотентности. `redis-stream` используется только как шина (и мок хранит в нём свои данные).

**Последствия.** Нагрузка на кэш и на стрим не конкурирует, каждый Redis можно масштабировать и настраивать
персистентность отдельно. Потеря `redis-data` сбрасывает только кэши и состояние идущих выполнений (они помечаются как
потерянные); аудит в PostgreSQL сохраняется.

## ADR-4. Один класс контроллера на эндпоинт

**Контекст.** SwooleApp направляет запросы по атрибуту `#[Route]` на классе контроллера.

**Решение.** Каждый эндпоинт — отдельный класс в `Wps\Controllers\…`, наследник `BaseController`, который добавляет
конверт ответа, отрисовку ошибок, помощники для разбора запроса и глобальные middleware.

**Последствия.** Эндпоинты маленькие, их легко найти по URI. Общая логика живёт в сервисах, а не в контроллерах.
Новый эндпоинт — новый класс; пространство имён контроллеров из `config.json` сканируется автоматически
(см. [Новый эндпоинт API](../07-developer-guide/extending/new-api-endpoint.md)).

## ADR-5. Реестры как точки расширения

**Контекст.** Новые типовые действия (отправка сообщения, вызов нестандартного API, новые способы загрузки объектов)
пишут разработчики, а бизнес-логика настраивается в интерфейсе (ответы №1, №12). Условия должны быть готовы к новым
операторам.

**Решение.** Четыре интерфейса с реестрами — `ActionHandlerInterface`, `ComparatorInterface`, `ChangeTypeInterface`,
`LoadStrategyInterface` — и `ExpressionEngine::registerFunction()`. В определении процесса хранятся только коды
(`type`, `operator`, `change_type`, `strategy`). Каждый обработчик сам проверяет свою настройку при сохранении
процесса. Эндпоинты справочников строятся по реестрам.

**Последствия.** Новая возможность — это один класс и одна строка регистрации в `Container`; она появляется в
справочниках интерфейса без изменений движка. После добавления нужен перезапуск (ответы №25, №26). Подписи, которые
возвращают реестры, — на русском; интерфейс переводит их по коду.

## ADR-6. Ленивая предзагрузка в условиях

**Контекст.** Условия могут сравнивать поля связанного объекта, загруженного из CRM (ответ №12). Если загружать его для
каждого события, CRM будет вызываться даже тогда, когда дешёвая проверка по объекту события уже не прошла.

**Решение.** Трёхзначная проверка условий (`ConditionEngineService`): сначала проверяются строки по `object.*`;
строка, которая ссылается на ещё не загруженную переменную, даёт «неизвестно». Только тогда выполняется блок `preload`,
и условия проверяются ещё раз. Плоский список строк объединяется по И; движок уже принимает дерево с
`logical_operator` `AND`/`OR`, поэтому ИЛИ и скобки можно будет добавить в интерфейс, не меняя движок (ответ №8).

**Последствия.** Большинство неподходящих событий вообще не доходит до CRM. Шаги предзагрузки, выполненные ради условий,
становятся первыми шагами выполнения и не повторяются.

## ADR-7. Идемпотентность по событию и однократный запуск для записи

**Контекст.** Доставка «хотя бы один раз» означает, что одно и то же сообщение может обработаться повторно. Отдельная
проблема — запись CRM сохраняется много раз, а процесс вроде «создать звонок по новому лиду» не должен запускаться при
каждом сохранении; условие на поле-маркер в CRM оказалось ненадёжным (`md/idempotentie_plan.md`, §1).

**Решение.** Два независимых механизма:
- `idem:{event_id}:{process_id}` в Redis (`SET NX`, 24 ч): повторно доставленное событие продолжает или пропускает уже
  существующее выполнение вместо нового запуска; для ведомых процессов ключ строится из родительского выполнения и шага;
- флаг процесса `run_once` и таблица `process_object_runs`: отметка «процесс × запись» ставится атомарно, когда условия
  выполнены, до старта выполнения, и блокирует повторы даже после `failed`, потому что действия не транзакционны
  (`md/idempotentie_plan.md`, FR-3). Снимается отметка явно — через API или интерфейс.

**Последствия.** Повторная доставка не даёт дублирующих побочных эффектов. Однократный запуск работает для любого
источника (`stream`, `child`, `manual`); `force` при ручном запуске пропускает только условия. Если в объекте нет `id`,
однократный запуск не применяется — это пишется в лог и считается метрикой (`wps_run_once_no_id_total`).

## ADR-8. Мягкое удаление процессов

**Контекст.** Выполнения ссылаются на процессы внешним ключом, а аудит должен оставаться читаемым после удаления
процесса.

**Решение.** `DELETE /api/processes/{id}` проставляет `deleted_at` и `is_active = false`
(`ProcessRepository::softDelete`); в комментарии миграции сказано: «soft delete keeps the execution audit consistent».
Процесс, на который ссылается `start_process` другого процесса, удалить нельзя (`409 PROCESS_IN_USE`).

**Последствия.** Старые выполнения по-прежнему показывают название и версию процесса. Удалённые процессы исчезают из
списков и из подбора, но остаются в базе.

## ADR-9. Состояние выполнения в Redis для продолжения после сбоя

**Контекст.** Результат каждого действия нужно хранить в Redis, пока процесс не завершён, а после завершения записывать
результат всего процесса в PostgreSQL (ответ №14); процесс, прерванный сбоем, нужно повторить и довести до конца
(ответ №22).

**Решение.** `exec:{uuid}` хранит контекст и `current_step` и обновляется после каждого шага; блокировка
`lock:exec:{uuid}` с коротким TTL обозначает владельца. Каждый шаг сразу пишется и в `execution_actions`, поэтому аудит
виден, пока выполнение идёт. `RecoveryJob` продолжает зависшие выполнения с `current_step` или помечает их упавшими,
если состояние потеряно.

**Последствия.** После сбоя повторяется не больше одного — прерванного — шага. Интерфейс может показывать живой
контекст идущего выполнения. Шаги должны переносить повторное выполнение (перед каждым повтором восстанавливается
снимок контекста).

## ADR-10. Расширять фреймворк, а не править его

**Контекст.** Часть поведения фреймворка не подошла: штатное сопоставление маршрутов сравнивает только длину шаблона
(`/api/processes/5` обслуживал бы контроллер `/api/processes`), `AbstractController` разбирает глобальные middleware,
но не запускает их, не было CORS preflight и JSON-ответов 404/500.

**Решение.** Наследование вместо правки кода в `vendor`: `WpsApplication extends Application` (preflight, JSON 404,
запасной 500), `WpsRoutesCollectionBuilder extends RoutesCollectionBuilder` (точное совпадение по числу сегментов),
`BaseController` (запускает глобальные middleware). Фреймворк — обычная зависимость Composer, версия зафиксирована в
`composer.lock`.

**Последствия.** Фреймворк обновляется через `composer update sidalex/swoole-app` без повторного наложения патчей;
при обновлении нужно проверить переопределённые методы.

## ADR-11. Конфигурация: сначала `.env`, затем окружение

**Контекст.** Сервис настраивается переменными окружения и файлами `.env`: сначала читается файл, затем настоящие
переменные окружения переопределяют или дополняют его (ответ №24).

**Решение.** `Wps\Kernel\Env::load()` переносит значения из `back/.env` в окружение, только если переменная ещё не
задана; `AppConfig::fromEnv()` читает всё один раз в мастер-процессе.

**Последствия.** Docker Compose и Kubernetes могут переопределить любое значение без правки файлов. Изменение
конфигурации требует перезапуска. Полный список — в разделе [Конфигурация](../04-operations/configuration.md).

## ADR-12. Ожидающие выполнения хранятся в PostgreSQL

**Контекст.** Пауза `delay` может длиться до 400 дней, длинные задержки повтора — минуты и часы. Держать такое
выполнение в корутине воркера нельзя (рестарт его теряет), а в Redis — ненадёжно: ключ `exec:{uuid}` имеет TTL, Redis
может потерять данные, и `RecoveryJob` пометит выполнение упавшим. Рассматривались варианты: A — отложенная очередь в
Redis (sorted set), B — таблица в PostgreSQL, C — внешний планировщик.

**Решение.** Вариант B. Выполнение паркуется: снимок состояния и срок пишутся в `execution_waits` в одной транзакции со
сменой статуса на `waiting`, после этого ключ в Redis удаляется. `WaitResumeJob` в каждом воркере забирает созревшие
строки через `FOR UPDATE SKIP LOCKED` с арендой и продолжает выполнение после CAS `waiting → running`. Удаление
процесса с ожидающими выполнениями требует `force=true` и отменяет их (`cancelled`); деактивация процесса их не
останавливает.

**Последствия.** Ожидание переживает перезапуск backend и потерю Redis (проверено `SIGKILL` посреди паузы), каждое
выполнение просыпается ровно один раз, ожидающие видны через `GET /api/executions?status=waiting`. Точность пробуждения
ограничена `WAIT_POLL_INTERVAL_MS`; размер снимка ограничен `WAIT_STATE_MAX_BYTES`. См.
[Надёжность → Ожидающие выполнения](../04-operations/reliability.md#ожидающие-выполнения).

## ADR-13. Плоская программа вместо обхода дерева

**Контекст.** Ветвления, циклы, досрочное завершение и `on_error: goto` не помещаются в линейный список шагов, а
восстановление после сбоя и аудит были построены на одном целом курсоре `current_step`
(`md/tasks_list/00-architecture.md`, раздел A).

**Решение.** Определение остаётся деревом (так его пишет пользователь), а перед выполнением компилируется в плоский
список инструкций (`action`, `branch`, `jump`, `jump_if_false`, `loop_begin`, `loop_next`, `halt`) с путями
`step_path`. Курсор — целое `pc`; стек циклов — `frames`; номер записи аудита — `seq`. `if / else-if / else` — одна
инструкция `branch` (одна запись аудита на блок, Q3). Блоки — отдельный реестр `BlockTypeRegistry`.

**Последствия.** Линейный процесс компилируется один в один (`seq == pc == прежний step_index`) — старые выполнения и
аудит совместимы. Восстановление после сбоя одинаково для любых блоков. Компиляция детерминирована и кешируется по хешу
определения; если хеш программы не совпал после обновления, выполнение не продолжается (`Program changed after an
upgrade`). См. [Движок выполнения](execution-engine.md#программа-и-инструкции).

## ADR-14. Свой контракт CRM 2.0 и два отдельных плагина

**Контекст.** Новым действиям нужны операторы фильтра, сортировка, курсор, подсчёт, удаление, связи и старые значения
полей в событии (раздел F, Q1). Встроенное API SuiteCRM V8 работает по OAuth2 и в другом формате.

**Решение.** WPS описывает **свой** контракт (`/api/v9`, [Интеграция с CRM](../04-operations/crm-integration.md)) —
расширение контракта 1.0 без поломки; CRM объявляет возможности через `GET /capabilities`, WPS проверяет их во время
выполнения (`CRM_CAPABILITY_MISSING`). Плагины SuiteCRM 7 и SuiteCRM 8 — два отдельных пакета вне репозитория, каждый
меняется и проверяется отдельно (`bin/contract_check.sh`). Событие v2: `event_type`, `before` **только изменённых**
полей (после нормализации по типу), `changed_fields`, `wps_origin` (раздел C). Фильтр — только AND (`in` / `nin` для
«или», Q28), сортировка — до 2 полей + `id` (Q27), агрегаты считает WPS (Q29).

**Последствия.** Любая CRM подключается, реализовав контракт (или адаптер-мост). Старый плагин продолжает работать в
пределах контракта 1.0. Событие без `event_type` трактуется как раньше (`legacy`). Отказ от отдельного эндпоинта
агрегатов означает чтение записей страницами (см. `AGGREGATE_MAX_RECORDS`).

## ADR-15. Журнал побочных эффектов и политика доставки

**Контекст.** Шаг выполняется «как минимум один раз»: после падения воркера `resume()` повторяет его. Для `PUT` в CRM
это безопасно, для письма или вебхука — нет (раздел H).

**Решение.** Таблица `step_side_effects` с ключом позиции вызова (`{pc}@{iteration}#{sub}`): `started` до вызова,
`done` с ответом после. Повтор шага с записью `done` возвращает сохранённый ответ; «чужая» запись `started` —
неизвестный исход, который по политике `delivery` либо даёт ошибку `UNKNOWN_OUTCOME` (`at_most_once`, по умолчанию для
писем, уведомлений, `POST`/`PATCH`), либо повторяет вызов с тем же `Idempotency-Key` / `Message-ID` (`at_least_once`).

**Последствия.** Дубликаты писем и заказов после сбоев исключены ценой редких `UNKNOWN_OUTCOME`, которые оператор
сверяет вручную. Действия CRM (связи, сохранения) идемпотентны и журнал не используют.

## ADR-16. Секреты: шифрование в приложении и ссылки `secret://`

**Контекст.** Действиям нужны пароли SMTP, токены API и ботов. Хранить их в определении процесса — значит раскрыть в
JSON, аудите, Redis и истории.

**Решение.** Таблица `secrets` с шифрованием XChaCha20-Poly1305 (libsodium) ключом `WPS_SECRETS_KEY`, ассоциированные
данные `wps-secret|имя|версия`, `kek_id` для ротации (`WPS_SECRETS_KEY_PREVIOUS` + `POST /api/secrets/rotate`). В
определении — только ссылка `secret://name[.field]`, и только в полях учётных данных; значения маскируются
`SecretMasker` в аудите и логах; расшифрованное значение живёт в памяти воркера `SECRETS_CACHE_TTL`.

**Последствия.** Значение секрета не возвращает ни один API. Потеря ключа означает повторный ввод секретов (процессы
менять не нужно). Без ключа сервис работает, но действия с секретами падают.

## ADR-17. Исходящие запросы: открыто наружу, закрыто внутрь

**Контекст.** `http_request` вызывает URL из определения процесса; редактор процесса не должен получить доступ к
внутренней сети (БД, Redis, метаданные облака) — Q20, Q21.

**Решение.** `EgressGuard`: любые публичные хосты разрешены, частные и служебные сети закрыты проверкой **всех**
адресов DNS, подключение — к уже проверенному IP (защита от DNS rebinding), редиректы проверяются заново; хост URL
задаётся только литералом; `http://` разрешён по умолчанию (`HTTP_ALLOW_PLAIN_HTTP=false` запрещает). Регулярные
выражения пользователей ограничены `SafeRegex` (длина, пределы перебора PCRE).

**Последствия.** Внутренние системы открываются явно (`HTTP_ALLOW_PRIVATE_CIDRS`); стенд разработки открывает сеть
docker и в прод не копируется. См. [Безопасность](../04-operations/security.md#исходящие-http-запросы-ssrf-защита).

## ADR-18. Сравнения: явный тип, отсутствующее поле — всегда «ложь»

**Контекст.** Все значения CRM приходят строками; метаданные полей CRM движок не читает (раздел E). Правило заказчика
№10: отсутствующее поле никогда не удовлетворяет условию.

**Решение.** Тип сравнения задаётся строкой условия (`cast`: `string`, `int`, `decimal`, `date`, `datetime`, `bool`,
`list`), приведение — один `TypeCaster` для условий, выражений и шаблонов; ошибка приведения — «ложь» с трассой (или
выполнение `failed` с шагом `conditions` при `on_cast_error: error`, Q8). `is_empty` для отсутствующего поля ложно;
отсутствие проверяется отдельными операторами `is_null` / `is_not_null` (Q7, решение заказчика). `decimal` и арифметика
`calculate` — через `bcmath` (Q15).

**Последствия.** Поведение условий предсказуемо и не зависит от CRM; пустая строка и отсутствие поля различаются.

## ADR-19. Время: часовой пояс бизнеса и только календарные единицы

**Контекст.** «Сегодня», начало месяца, `date_shift` и паузы зависят от пояса; заказчик исключил рабочие дни и
производственный календарь из скоупа (раздел J, O).

**Решение.** `WPS_TIMEZONE` (IANA, по умолчанию UTC) для календарных операций; даты CRM — UTC; часы и минуты считаются
точным временем (`+1d` ≠ `+24h` при переходе на летнее время). Время берётся только через `Wps\Time\Clock`
(`FrozenClock` в тестах). Новые таблицы — `TIMESTAMPTZ`, сравнения сроков ожиданий — по `now()` PostgreSQL.

**Последствия.** Нет `workday` / `add_workdays`; расширение — новая единица в `DateMath` и функции выражений. Неверный
пояс останавливает сервис при старте.

## ADR-20. Свой шаблонизатор с экранированием по полю

**Контекст.** Тексты писем, HTTP-тел и уведомлений собираются из данных CRM; Twig слишком широк для бизнес-пользователей
(раздел G).

**Решение.** `TemplateEngine`: `{{ path | фильтр }}`, `{{= выражение }}`; фильтры — те же функции выражений. Режим
экранирования выбирает **потребитель поля** (`text`, `header`, `html`, `url`, `json`), а не автор шаблона; хост URL
шаблонизировать нельзя; отсутствующее значение — по политике поля (`empty`, `error`, `keep`).

**Последствия.** Один набор функций для выражений и шаблонов; header-injection и подмена хоста исключены конструкцией.

## ADR-21. Обработанные ошибки не меняют статус `completed`

**Контекст.** `on_error: continue / goto` и `on_item_error: continue` позволяют процессу дойти до конца после ошибки
шага (Q4); блок-обработчик ошибок уровня процесса отложен (Q5).

**Решение.** Выполнение с обработанными ошибками — `completed`; число ошибок — `executions.handled_errors`, метрика
`wps_step_errors_handled_total`, последняя ошибка — `sys.last_error`. `goto` — только вперёд на шаг верхнего уровня;
пропущенные им шаги в аудит не пишутся (Q6). `stop_process` с `failed` — не ошибка шага, `on_error` его не перехватывает.

**Последствия.** Статусы остаются простыми; «успешные с ошибками» выполнения видны по счётчику и метрике.

## ADR-22. Зарезервированные имена и упорядоченные списки в определении

**Контекст.** Системные значения (`sys`), константы (`config`) и старые значения (`object_before`) читаются как
переменные (раздел I); `definition` хранится в `jsonb`, который не сохраняет порядок ключей объектов (L.14).

**Решение.** Имена `object`, `object_before`, `sys`, `config` зарезервированы (`ExecutionContext::RESERVED`), последние
три — только для чтения, `sys` и `config` вычисляются при чтении. Миграция 010 сообщает о процессах, где эти имена
использовались как переменные. Везде, где важен порядок (`actions`, `branches`, поля `set_variable`, правила
`update_records`, записи `map`), формат использует списки.

**Последствия.** Порядок вычислений не зависит от хранения. Процессы со старыми именами после обновления выполняются, но
не сохраняются, пока переменные не переименованы.

## ADR-23. Что сознательно не сделано

| Что | Решение | Где |
|---|---|---|
| Запуск по расписанию (cron), триггер по дате в записи | Вне P1/P2 (решение заказчика) | `md/tasks_list/_excluded/` |
| Рабочие дни, рабочие часы, производственный календарь | Исключены | ADR-19 |
| Outbox в плагине CRM | Нет: при недоступном Redis событие теряется, сохранение в CRM проходит | [Надёжность](../04-operations/reliability.md#что-не-гарантируется) |
| ИЛИ и скобки в условиях в интерфейсе | Движок принимает дерево, интерфейс — плоский список | ADR-6 |
| Канал email в `notify` | Не делается — есть `send_email` (Q23) | — |
